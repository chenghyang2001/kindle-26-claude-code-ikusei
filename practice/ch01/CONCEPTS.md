## 1. Vibe Coding（氛圍式開發）

### 是什麼

- 由 Andrej Karpathy 在 2025 年提出：開發者用自然語言描述想要的結果，讓 AI 產生程式碼，自己主要負責「看結果、給回饋、再修正」，不一定逐行閱讀程式碼。
- 重心從「怎麼寫」轉成「要什麼」：人當產品經理＋驗收者，AI 當實作者。

### 優點

- 上手門檻低，非工程背景也能做出可運作的原型。
- 迭代速度快，適合 demo、個人小工具、探索想法。

### 風險與限制

- **看不懂就無法維護**：程式碼一多，出錯時難以定位。
- **品質不穩定**：同樣的描述，每次產出可能不同；邊界情況、錯誤處理、安全性容易被忽略。
- **需求模糊會被放大**：AI 只能依你說的猜，描述越含糊，偏離越遠。
- 結論：Vibe Coding 適合「快速驗證」，正式專案需要搭配規格、測試與審查。

### 在 Claude Code 裡怎麼體現

在終端機輸入一句話：

```text
> 做一個單檔 HTML 的番茄鐘，有開始／暫停／重設按鈕，倒數結束時發出提示音
```

Claude Code 會自己建立 `index.html`、寫入 HTML/CSS/JS，你打開瀏覽器看效果，再回一句「按鈕改大一點、加上深色模式」繼續修。整個過程你沒寫任何一行程式碼——這就是 Vibe Coding。本練習專案 `CLAUDE.md` 中「快速 demo 模式」（不跑 QA、只求看懂流程）也是同樣的取捨。

## 2. LLM 運作原理

### 核心機制：預測下一個 token

- LLM（大型語言模型）把文字切成 **token**（字詞片段），根據前文計算「下一個 token 的機率分布」，再一個一個生成。
- 它不是查資料庫，而是從大量訓練資料中學到的「統計規律」；因此可能產生看似合理但錯誤的內容（**幻覺**）。

### 幾個影響使用方式的關鍵概念

| 概念 | 說明 | 對開發的影響 |
| --- | --- | --- |
| Context Window（上下文視窗） | 模型一次能「看到」的 token 上限 | 對話太長、檔案太多會被壓縮或遺忘，要精簡給資訊 |
| 無狀態（Stateless） | 模型本身不記得上一次對話，記憶來自每次重新送進去的內容 | 專案規則要寫在檔案裡，每次自動載入 |
| 隨機性（Temperature） | 生成帶有隨機成分 | 同一指令結果可能不同，要靠測試驗證，不能只信一次輸出 |
| 知識截止（Knowledge Cutoff） | 訓練資料有截止日期 | 新版套件、API 可能不知道，需提供文件或讓它查詢 |
| 工具使用（Tool Use） | 模型可輸出「呼叫某工具」的指令，由外部程式執行再把結果送回 | 讓 LLM 從「只會說」變成「能讀檔、跑指令、改程式」的 Agent |

### 在 Claude Code 裡怎麼體現

- **CLAUDE.md 對應「無狀態＋上下文」**：模型不會記住你上次說過的規則，所以 Claude Code 每次啟動都會自動把專案的 `CLAUDE.md` 讀進 context。本專案的 `CLAUDE.md` 寫了「豁免三 agent 鐵律、選擇題採推薦選項」，Claude 就是靠這個檔案「記得」這些規則。
- **Context 管理**：對話太長時可用 `/compact` 壓縮、`/clear` 清空，避免超過上下文視窗導致前面資訊被遺忘。
- **Tool Use 的實際樣子**：你說「看一下這個資料夾有什麼」，Claude Code 不是憑空回答，而是呼叫 Bash 執行 `ls`，拿到真實結果後才回覆——這就是 LLM 透過工具取得事實、降低幻覺的方式。

## 3. Spec Driven Development（規格驅動開發）

### 是什麼

- 先寫清楚**規格（Spec）**，再讓 AI 依規格實作。規格是人與 AI 之間的「合約」。
- 典型流程：**需求（Requirements）→ 設計（Design）→ 任務拆解（Tasks）→ 實作 → 驗證**。

### 規格通常包含

1. **目標**：要解決什麼問題。
2. **輸入／輸出**：接受什麼、產出什麼。
3. **核心邏輯**：條列步驟（不寫程式碼）。
4. **邊界條件**：空輸入、錯誤輸入、極端值怎麼處理。
5. **驗收標準**：怎樣算完成（可對應到測試）。

### 和 Vibe Coding 的對照

| 面向 | Vibe Coding | Spec Driven Development |
| --- | --- | --- |
| 起點 | 一句話想法 | 一份規格文件 |
| 適合 | 原型、demo、探索 | 正式專案、多人協作、長期維護 |
| 品質控制 | 靠肉眼看結果 | 靠規格＋測試＋審查 |
| AI 的自由度 | 高（容易偏離） | 受規格約束（結果可預期） |

兩者不是對立：常見做法是先用 Vibe Coding 探索，確定方向後寫成規格，再用規格驅動正式實作。

### 在 Claude Code 裡怎麼體現

1. 先請 Claude Code 寫規格而不是程式碼：

   ```text
   > 我要做一個 CSV 轉 JSON 的 CLI 工具。先不要寫程式，
     幫我寫 docs/spec.md，包含目標、輸入輸出、邊界條件、驗收標準。
   ```

2. 用 **Plan Mode**（`Shift+Tab` 切換）讓 Claude 只規劃、不改檔，你確認計畫後才放行實作。
3. 確認後再說「依照 `docs/spec.md` 實作，並為每條驗收標準寫測試」，最後跑測試驗證。

規格檔放在 repo 裡，下次開新 session 時 Claude 讀得到，不會因為對話被壓縮而「忘記需求」——這同時呼應了第 2 段 LLM 無狀態的特性。
