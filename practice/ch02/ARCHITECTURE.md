# ARCHITECTURE.md — Claude Code 運作架構

> K26《Claude Code 育成手冊》第 2 章練習：用自己的話整理 Claude Code 的內部運作。

## 1. LLM 工具呼叫（Tool Use）

語言模型本身只會「產生文字」，它不能直接讀檔、跑指令或上網。工具呼叫就是讓它能做到這些事的機制：

1. **宣告工具**：啟動時，Claude Code 把可用工具（Read、Write、Edit、Bash、Grep、Glob、WebFetch、MCP 工具……）的名稱、用途與參數 JSON Schema 一起放進給模型的提示裡。
2. **模型決定呼叫**：模型判斷需要外部資訊或動作時，不直接回答，而是輸出一個結構化的 `tool_use` 區塊，例如：

   ```json
   { "type": "tool_use", "name": "Read", "input": { "file_path": "src/app.py" } }
   ```

3. **客戶端執行**：真正執行工具的是 Claude Code（客戶端），不是模型。執行前會經過權限檢查與 hooks。
4. **結果回填**：執行結果包成 `tool_result` 放回對話，模型在下一輪看到結果後再決定下一步。

重點：模型負責「決定做什麼」，Claude Code 負責「實際去做」並把結果送回去。

## 2. Agent 協作迴圈（Agentic Loop）

Claude Code 不是一問一答，而是一個會反覆執行到任務完成的迴圈：

- **收集脈絡**：讀 CLAUDE.md、搜尋檔案、讀程式碼。
- **採取行動**：編輯檔案、執行指令。
- **驗證結果**：跑測試、看輸出、檢查錯誤。
- **判斷是否結束**：模型的回應不再包含工具呼叫（`stop_reason` 不是 `tool_use`）時，迴圈結束，把最終文字回給使用者。

需要時，主 agent 還能用 Agent 工具派出 **sub-agent**。sub-agent 有自己乾淨的 context，做完只回傳摘要，避免主對話被大量搜尋結果塞滿。這就是「協作」的部分：主 agent 當指揮，sub-agent 分頭做事。

## 3. 沙箱執行（Sandboxing）

模型可以要求執行任意 Bash 指令，所以必須有防護：

| 防護層 | 作用 |
| --- | --- |
| 權限模式 | 預設每個有副作用的工具都要使用者同意；也可設 allow / deny 規則（`.claude/settings.local.json`） |
| 沙箱 | 限制指令能寫入的檔案路徑（通常只限專案目錄）與能連的網路網域，由作業系統層級強制 |
| Hooks | `PreToolUse` 可在執行前攔截、`PostToolUse` 可在執行後檢查 |
| 工作目錄範圍 | 預設只能讀寫啟動目錄及其子目錄 |

好處：模型就算判斷錯誤或被提示注入，影響也被限制在沙箱範圍內，不會動到系統其他地方。

## 4. 五大開發階段

Claude Code 適合把一個開發任務拆成五個階段，每個階段都在上面的迴圈中進行：

| 階段 | 做什麼 | 常用工具 / 功能 |
| --- | --- | --- |
| 1. 探索（Explore） | 理解專案結構、找相關程式碼 | Glob、Grep、Read、Explore sub-agent |
| 2. 規劃（Plan） | 拆解步驟、決定改哪些檔案 | Plan 模式、Plan agent、規格文件 |
| 3. 實作（Code） | 修改與新增程式碼 | Edit、Write |
| 4. 驗證（Test） | 跑測試、看輸出、修正錯誤 | Bash（測試指令）、瀏覽器截圖 |
| 5. 提交（Commit） | 整理變更、寫 commit message、開 PR | Bash（git）、gh CLI |

```
探索 ──► 規劃 ──► 實作 ──► 驗證 ──► 提交
                   ▲        │
                   └────────┘  驗證失敗就回到實作
```
